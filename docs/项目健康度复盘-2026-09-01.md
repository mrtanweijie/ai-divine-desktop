## 二、后端（app 48,511 行）

### 核心问题 1：api/chat.py 巨型化（1,616 行）

13 个 `_detect_*` 启发式意图函数（_detect_simple_chat/extract/rewrite/calc/qa/local_task 等）与 `agent/intent/intent.py` 的 classify_intents **职责重叠（意图检测双轨）**，且路由 + SSE + 本地聊天全挤在一个文件。

### 核心问题 2：两处 async 阻塞（高）

| 位置 | 问题 |
|---|---|
| `agent/orchestrator.py:312` | classify_intents 在 async generator 中直接同步调用（本地模型开启时 manager.classify() 为阻塞 HTTP 1-2s）|
| `agent/middleware/middleware.py:25/32` | TodoSyncMiddleware 在 async 中直接同步 SQLite |

另有中风险：`api/chat.py stream_chat` 内大量直接同步 db 调用（:104/:132/:147/:163/:193）。

### 中间件真相
实际是 **8 个 langchain middleware**（tools.py:216-247）：ReActParse → dynamic_prompt → ModelCallLimit → ToolCallLimit → HumanInTheLoop → TodoSync → TodoList → ToolError。TodoSync 顺序依赖 HumanInTheLoop 设置的 `plan_first_pending`，react 切换敏感。

### 异常处理三模式并存
① HTTPException 派（多数 router）② SSE error_event 派（chat.py 12 处）③ 裸返回派（mcp.py 0 try/0 except、settings、terminal）——**无全局 exception_handler**。

### 其他
- 根目录平铺 11 个 .py（986 行）：`github_skills.py`/`skills.py` 是纯 re-export 壳；`document_reader`/`file_types` 可并入 `tools/readers/`；杂项未归子包
- 魔法值散落：端口 8016（local_llm.py:78/79 与 config 重复）、`_CHUNK_CHARS=2000`、`_CACHE_TTL=300`、阈值 0.75（orchestrator.py:49 与 intent.py:381 重复）、慢请求 1000ms、截断 12000 字符
- 无死代码，TODO/FIXME 全项目仅 6 处；to_thread 使用 40+ 处总体规范
- docgen/pdf 子包仍有 6 个大文件（theme_colors 780 / cover_builder 710 / recipes 628 / design_rules 548 等）

## 三、工程化（发布链路是重灾区）

### 严重度【高】自动更新链路当前是断的
- `release-assets/latest.json` url 字段损坏：`https://github.com/https://git.duguying.net/ai-divine/...`（双重前缀，下载必 404）
- **根因**：`scripts/publish-macos.sh:203` 构造 `https://github.com/$REPO/...`，但 `REPO` 从 git remote 推断的 sed 正则只认 `github.com`（:185-188），而真实 remote 是 Gitea `git.duguying.net` → 推断失败 REPO 为空，仍走了非 REPLACE 分支
- `tauri.conf.json` plugins.updater.endpoints 指向 `https://github.com/mrtanweijie/...`（旧仓库），与 Gitea remote 不符

### 严重度【高】CI 双轨且无质量门禁
- `.github/workflows/build.yml`（4 平台）**实际不生效**：remote 是 Gitea
- 实际 CI 是 `.gitea/workflows/release-macos-universal.yaml`：仅 macOS 签名+公证+发 Release，**不跑任何 test/lint**
- Win/Linux 跨平台构建无有效 CI 承接
- **两条 workflow 均不跑 pytest / cargo test / 前端 lint**

### 严重度【中】工程化基建缺位
- 前端：tsconfig strict:true 且 build 强制 `tsc -b`（唯一自带质量闸），但**无 eslint/prettier**，无 lint/format 脚本
- 后端：**无 ruff/mypy**、无 pyproject
- 测试：64 文件无 conftest/pytest.ini、无覆盖率工具、无统一命令；`.pytest_cache/lastfailed` 有 4+ 条失败用例未清
- 依赖：React 19.2.8 / TS 7.0.2 / Vite 8.2.1 激进；langchain 固定版本三件套；`thinking-orbs@0.2.0` 小众包

### 发布脚本过时（中）
scripts/ 三件套以 GitHub 为目标（`overwrite-release.sh` 默认 REPO=mrtanweijie/ai-divine-desktop 旧仓库），与 Gitea CI 并存。fastlane 签名/公证链路本身完整。

### Rust 壳（亮点，仅 1 低风险）
- sidecar 生命周期监管完整（`services/sidecar.rs` spawn/5s 探活/120s 宽限/重启）
- 非测试 expect 仅 2 处，unsafe 仅 1 处（objc2 FFI 必需）
- 低：monitor 线程无停止标志，stop 后探活线程仍可能尝试重启；start 可重复 spawn 多 monitor 线程
