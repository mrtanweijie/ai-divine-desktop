# 本地预整理（长文本输入侧预处理）功能设计

> 版本：v1.0
> 日期：2026-08-29
> 状态：已实现（后端 `preprocess.py` + `organize()` + chat/settings/sessions 接线 + 19 项测试；前端「已本地整理」徽标 + 可展开原文卡片）
> 关联模块：`divine-server/app/agent/preprocess.py`（新增）、`divine-server/app/agent/local_llm.py`（新增 `organize()`）、`divine-server/app/api/chat.py`、`divine-server/app/config.py`、`divine-server/app/api/settings.py`、`divine-server/app/api/sessions.py`、`divine-app/src/pages/chat/`（前端"已本地整理"标记 + 原文附件卡片）、`divine-app/src/types.ts`、`divine-app/src/services/api.ts`

## 1. 背景与目标

用户经常直接粘贴一大段文字（会议纪要、报错日志、聊天记录、需求文档）给 Agent。长文本直接进云端模型有两个问题：

- **贵且慢**：长输入按 token 计费，云端处理全量原文；
- **信息密度低**：原文夹杂大量废话、重复、无关内容，云端模型要在噪声里找重点。

本设计引入**输入侧本地预整理**：用户粘贴长文本时，本地小模型先把原文整理成结构化版本（分段 + 要点 + 关键事实），云端模型基于整理版工作；原文自动转存为工作区附件，云端需要细节时按需读取。

**为什么这个任务适合本地小模型**：整理/结构化/提炼要点是"模式匹配 + 提取"，是小模型的舒适区；且下游云端模型会再加工，本地整理质量要求是"够用"，不是"完美"——与意图分类（要求判别精确）不同，这是本地小模型最能发光的场景。

### 目标

- 长文本输入（默认 >800 token，用 `estimate_tokens` 估算，中英文公平）自动触发本地整理（默认开，可在设置关闭）；用户也可显式要求整理（"整理/梳理/归纳/总结 + 指向文本"才触发，防"帮我整理房间"这类日常用法误触发）。
- 整理版作为消息内容进入会话与云端上下文；原文自动存为工作区附件，云端可读。
- 本地模型不可用或整理失败时**原样上云**，绝不吞消息、不阻塞对话。
- 整理版与原文同时落库，形成数据闭环（后续可评估整理质量、决定是否微调）。

### 非目标

- 不做"推理式重组"：不判断原文对错、不补全缺失逻辑、不把笔记"重写"成方案——那是云端模型的活。
- 不改动现有 `summarize()`（对话历史压缩）与 `compact.py`（上下文截断）：它们是**历史侧**能力，本功能是**输入侧**预整理，互不干扰。
- 首版不覆盖定时任务（scheduler）路径，只处理聊天（chat）路径。

## 2. 触发规则（自动 + 显式）

| 触发方式 | 条件 | 说明 |
|---|---|---|
| 显式 | 指令词（`整理`、`梳理`、`归纳`、`总结`、`帮我理一下`、`organize` 等）**且**命中文本指代词（`这段`、`这个`、`以下内容`、`上面的话`、`上面的文字` 等） | 防"帮我整理房间的计划"这类日常"整理"误触发（决策 1）；无论多短都触发；本地不可用时原样上云（云端自己处理） |
| 自动 | 文本 token 估算 > `local_llm_preprocess_threshold`（默认 800 token，用现有 `estimate_tokens`，中英文公平）且本地模型可用且非代码、非表格、非指针文本 | 默认开（`local_llm_preprocess_auto=true`，可关，决策 2）；代码/表格/指针必须原样给云端 |

优先级：显式 > 自动。

**代码检测**：文本含 Markdown 代码围栏（```），或代码特征密度高（大量行以空格/制表符缩进、含 `{}` `;` `=>` 等符号、换行密度高）→ 判定为代码，自动模式跳过；显式模式仍可整理（整理的是结构说明，不是代码本身）。

**指针检测（链接 / 本地路径）**：链接与路径是"指向内容的指针"，不是"待整理的内容"——对指针做整理没有意义（本地模型只会把 URL/路径当字符串复述或曲解）。检测规则：

- URL：含 `https?://` 或 `www.`；
- 本地绝对路径：复用 `intent.py` 的 `_ABS_PATH_RE`（`/Users/...`、`~/...`、`C:\...` 等）；
- 命中且消息**基本就是**指针（去掉指针后剩余内容为空或极短）→ **跳过整理，原样上云**，由云端用对应工具处理：路径 → `read_file` / `read_image` / `document_reader`，链接 → `web_fetch` / `web_search`；
- 混合场景（长文本中夹带链接/路径）→ 仍整理，但 `organize()` 的 prompt 硬性要求"保留所有链接、路径、专有名词，原样不改写"。

> 现有行为佐证：`intent.py` 的 `_ABS_PATH_RE` 注释明确"纯路径消息应交给云端读取文件（read_file/read_image），而不是误执行本地动作"——指针消息走云端的链路已存在，本设计只是保证整理功能不横插一脚。

## 3. 数据流

```
用户粘贴长文本
   │
   ▼
chat.py stream_chat
   │
   ├─ 显式整理指令（词+指代词）？ ──是──┐
   ▼                       │
  token>阈值 && 非代码/表格/指针？ ──是──┤
   │ 否                    │
   ▼                       ▼
原样保存消息          本地模型可用（is_ready）？
                      ├─ 是 → organize()（超长分块）
                      │      ├─ 成功 → 整理版 + 原文存附件 → 云端处理
                      │      └─ 失败/超时 → 原样上云
                      └─ 否 → 原样上云
```

关键约束：

- 预处理在消息入库**之前**完成：消息内容 = 整理版（或原样），附件引用随消息走现有 `Attachment(file_path=…)` 机制。
- 整理版前注入一行系统提示：`用户原文已保存为工作区附件，整理版可能有遗漏，关键信息请读附件核对。`——防止整理错误导云端，也是防"整理错比不整理糟"的保险。

## 4. 整理输出格式契约

`organize()` 的 few-shot prompt（仿 `classify()` 的"钉死格式"思路）：

```
你是文本整理助手。把用户输入整理成结构清晰的版本：
1. 按主题分段，每段用「### 标题」+ 要点列表
2. 保留所有关键事实、数字、名称、约束条件，不改写原意
3. 删除重复、客套、无关内容
4. 不添加原文没有的信息，不判断对错
5. 保留所有链接、路径、专有名词，原样不改写；表格/CSV 等结构化内容保持原格式
6. 输出以「[本地整理版]」开头；无法整理时只输出「无法整理」
```

输出示例：

```
[本地整理版]

### 背景
- …

### 需求
- …

### 关键事实 / 约束
- …
```

模型参数：`temperature=0.2`（结构化输出，求稳可 0.0）、`max_tokens` 按输入长度缩放（如 `min(len(text)//2, 2048)`）。

## 5. 核心实现改动点

### 5.1 `divine-server/app/agent/local_llm.py` — 新增 `organize()`

仿现有 `summarize()`（第 533-585 行）的调用模式：

- `def organize(self, text: str, timeout: float = 30.0) -> str | None`：调 llama-server `/v1/chat/completions`，返回整理文本；失败返回 `None`（调用方降级）。
- 处理 `max_tokens` 截断风险：若输出被截断（`finish_reason == "length"`），丢弃该结果返回 `None`，交给云端——半截整理版比不整理更糟。
- **输出三关校验**（任一不过即丢弃返回 `None`，宁可不整理）：① 不以 `[本地整理版]` 开头；② 长度 > 原文 80%（废话整理）；③ 明显乱码（不可打印字符占比高）。

> **实现记录（2026-08-29，真实 1.5B 模型验证）**：校验 ① 实际放宽为"以 `[本地整理版]` 开头 **或** 以 `### ` 标题开头"——Qwen2.5-1.5B 实测会正确输出 `###` 分段但漏掉前缀标记（小模型对"输出以 X 开头"这类元指令跟随弱）。配套措施：prompt 增加 few-shot 示例（小模型吃示例不吃规则），示例后 1.5B 即输出完整 `[本地整理版]` 格式（0.7s/次）。分块重标注逻辑同步处理两种开头（`[本地整理版]` 替换首行 / `###` 前置标注保留标题）。
>
> **实现记录 2（附件通道，2026-08-29）**：前端 `savePasteText` 把大段粘贴存成 `paste-*.txt` 文件再以附件发送（`Attachment(file_path=…)`），**"贴长文本"实际走的是附件通道而非 question 文本**。为此 `chat.py` 在附件循环里对纯文本附件调用 `maybe_preprocess_attachment()`（见 §5.3）：显式 = question 含整理指令词（附件即指代对象）；自动 = 内容 token 超阈值且非代码/表格。整理版替换附件 content（进模型上下文），原文仍是附件自身（approved_paths + read_file 可读），`preprocess` 部件落库供前端。
>
> **实现记录 3（真实模型参数，2026-08-29）**：`organize()` 两个参数经真机调优——① `max_tokens` 从 `len//2` 改为 `min(max(len//2, 1536), 2048)`：1.5B 整理 1500+ 字输入常输出 800+ token，原值会截断导致整段整理被丢弃；② 校验 ② 从"长度 > 原文 80%"改为"长度 > 原文 1.5x+200 且无 `###` 标题"：密集内容的重构输出（加标题/要点化）与原文等长甚至更长，80% 会误杀合格整理（实测 1731 字输入输出 1823 字、结构完整，被旧规则丢弃）。
>
> **实现记录 4（自动拉起模型，2026-08-29）**：实测发现 App 的 sidecar 会周期性重启，且每次重启把 8016 上的 llama-server 当"孤儿"杀掉（`_free_orphan_port`），导致本地模型"起得来留不住"，预整理频繁静默降级云端（用户连续 3 次"整理文件内容/帮我整理"+大附件全走了云端，单次烧 2.7 万 token）。修复：`preprocess._start_local_model()`——预整理触发时若 `is_ready()` 为 False，自动用已装模型（设置里的 local_llm_model → 优先 1.5B → 第一个已装）拉起 llama-server 并等就绪（最长 40s），成功才整理；无模型/失败/超时再降级云端。真实环境验证：8016 停机状态下触发预整理，15s 冷启动 + 整理成功。
>
> **实现记录 5（输出截断修复，2026-08-29）**：用户 107KB 附件实测仍走云端，App 日志显示根因是**分块整理输出被 `max_tokens` 截断**（`本地整理失败（第 2/5 块）`）→ 按"半截丢弃"设计整体放弃上云。两个修复：① prompt 新增"尽量简洁，每个要点一句话，不要逐条复述原文"；② `max_tokens` 改为 `min(max(len(text), 1024), 2048)`（2000 字分块给足 2048）。真实模型验证：2312 字分块 6.5s 输出 908 字、未截断。注意：分块越多越容易在某块截断，若仍偶发，可降低单块字数（2000→1500）。
>
> **实现记录 6（失败询问用户，2026-08-29）**：用户明确要求"整理失败后询问是否走云端"。实现：`maybe_preprocess`/`maybe_preprocess_attachment` 返回值增加 `attempted` 标记（触发但失败 = attempted=True）；chat.py 在云端调用前检测到 `attempted and not organized` 时，复用终端审批机制（`create_terminal_decision` + SSE `tool` 事件 `confirm_type="preprocess_fallback"` + `POST /api/terminal/decide`）弹确认卡"长文本本地整理失败，直接交给云端将消耗较多 token。是否继续？"；用户取消 → 回复"已取消，未调用云端"+ done；180s 超时按取消处理。前端 `ToolStatusCard` 新增 `preprocess_fallback` 确认卡分支（提交沿用统一的 `/terminal/decide`）。端到端验证：模型停机 → 确认卡出现 → 批准后走云端 / 取消后无云端调用。

### 5.2 `divine-server/app/agent/preprocess.py`（新模块）

```
def maybe_preprocess(
    text: str,
    session_id: str,
    workspace: Path,
) -> tuple[str, Path | None, bool]:
    """返回 (最终消息文本, 原文附件路径或None, 是否已整理)。"""
```

职责：

0. 指针检测：消息基本是 URL / 本地绝对路径（复用 `_ABS_PATH_RE`）→ 直接返回原样，不整理（见 §2 指针检测）。
1. 触发判断：显式 = 指令词 + 文本指代词双命中（§2，决策 1）；否则 token 估算 > 阈值且非代码、非表格、非指针且本地可用 → 自动整理。
2. 表格检测：多行同分隔符（`,` `\t` `|`）且列数一致 → 判定为表格/CSV，自动模式跳过。
3. 多轮退化检测：输入与最近附件原文相似度高（如 `difflib` 相似度 > 0.8）→ 不重复整理，原样上云。
4. 调用 `get_manager().organize()`；不可用/失败/超时 → 返回 `(text, None, False)`。
5. 分块整理（见 §6）：`>2500` 字分块，每块 ~2000 字，上限 5 块，拼接标注「（第 N 部分）」。
6. 原文写入 `workspace / "sessions" / session_id / "attachments" / f"original-{ts}.md"`（与截图存 `workspace/screenshots/` 同风格；`files.py` 根目录含 `workspace_dir()`，`read_file` 工具白名单为 workspace 内路径——已确认可读）。
7. 组装注入提示：整理版前缀附 §3 的核对提示。

### 5.3 `divine-server/app/api/chat.py`

`stream_chat` 入口（第 42 行起）在消息入库前调用 `maybe_preprocess`：

- 消息内容存整理版；`original_attachment` 作为 `Attachment(file_path=…)` 附加；
- 前端 SSE 事件里带 `organized: true` 标记（供 UI 显示"已本地整理"）；
- **附件通道**：附件循环里对纯文本附件调用 `maybe_preprocess_attachment(question, content, …)`——粘贴的大段文本（`paste-*.txt`）先本地整理再上云：整理版替换附件 `content`（进模型上下文），原文仍是附件自身（approved_paths + read_file），`preprocess` 部件（order=100+index）落库。显式触发 = question 含整理指令词（附件即指代对象）；自动 = 内容超阈值且非代码/表格。

### 5.4 配置与设置

- `divine-server/app/config.py`：`local_llm_preprocess_enabled`（总开关，默认 true）、`local_llm_preprocess_auto`（自动触发开关，默认 true；显式触发不受影响）、`local_llm_preprocess_threshold`（默认 800 token，`estimate_tokens` 估算）、`local_llm_preprocess_code_skip`（默认 true）。
- `divine-server/app/schemas.py`：`StreamChatRequest` 无需改；如需回传状态，在 SSE 事件结构或消息扩展字段中加 `organized`。
- `divine-server/app/api/settings.py`：`_public()` 暴露新设置。

### 5.5 前端 `divine-app`

- 发送长文本后：整理进行中显示状态（1-3s；并发排队时显示"正在排队整理"，最长等待受 30s 超时兜底）；
- 自动触发时消息旁显示「已自动整理，点击查看原文」（决策 2）；显式触发显示「已整理」；
- 消息下方固定显示「原文附件」卡片（可展开）——**历史刷新时用户必须能看到原文**，否则会以为原文被"吃"了；
- 会话清空时随会话删除 `attachments/` 目录（决策 4）——删除路径为 `workspace/sessions/{sid}/attachments/`（与 `preprocess.py` 落盘位置一致，实现时已修正一次路径不一致）。

## 6. 分块策略（现有 ctx 4096 必须处理超长输入）

| 输入长度 | 策略 |
|---|---|
| ≤ 2500 字符 | 单次整理 |
| 2500 ~ 10000 字符 | 分块整理：每块 ~2000 字，上限 5 块，拼接并标注「（第 N 部分）」 |
| > 10000 字符 | 只整理前 5 块，超出部分仅进原文附件，整理版注明「更早内容见附件」 |

分块边界按段落切（优先在 `\n\n` 处断开），避免切断语义。

## 7. 质量保险

1. **原文保真**：原文始终存附件，云端有 read_file 能力可读，整理错不致命。
2. **核对提示**：整理版前缀提示云端"可能有遗漏，关键信息读附件核对"。
3. **半截丢弃**：`finish_reason == "length"` 的输出直接丢弃，宁可不整理。
4. **输出三关校验**：不以 `[本地整理版]` 开头 / 比原文还长 / 乱码 → 丢弃（见 §5.1）。
5. **数据闭环**：整理版 + 原文 + 最终回答均落库 → 可离线评估整理质量（是否丢关键信息、是否曲解），为"补 prompt / 换 1.5B / 微调"提供依据。

## 8. 边界情况与决策（P0 不做就出错 / P1 影响体验 / P2 留 v2）

| # | 场景 | 处理 | 优先级 |
|---|---|---|---|
| 1 | "帮我整理房间的计划"（日常"整理"） | 显式触发要求指令词 + 文本指代词双命中，否则原样上云（决策 1） | P0 |
| 2 | 用户故意贴长文让云端逐字分析 | 自动整理改变语义 → 前端必显「已自动整理，点击查看原文」+ 附件保真 + 设置可关（决策 2） | P0 |
| 3 | 整理输出不以 `[本地整理版]` 开头 / 比原文还长 / 乱码 | 三关校验不过 → 丢弃走云端（§5.1） | P0 |
| 4 | 输出被 `max_tokens` 截断 | `finish_reason == "length"` → 丢弃走云端 | P0 |
| 5 | 第二轮"再整理一遍"（输入已是整理版） | 与最近附件原文相似度 > 0.8 → 不重复整理 | P1 |
| 6 | 历史刷新只见整理版 | 前端必须展示「原文附件」卡片 | P1 |
| 7 | 后续轮次引用原文细节（"第三点仔细说说"） | 云端默认不注入原文（省 token，决策 3）；核对提示引导"必要时读附件" | P1 |
| 8 | 中英文长度差异 | 阈值按 `estimate_tokens` 估算（默认 800 token），不按字符 | P1 |
| 9 | 表格 / CSV / JSON 日志 | 表格特征检测 → 自动模式跳过；显式整理时 prompt 要求保留原格式 | P1 |
| 10 | 两个会话同时贴长文（单实例串行） | 排队；30s 超时兜底 + 前端「正在排队整理」 | P1 |
| 11 | 原文附件明文落盘（密钥/合同） | 本地应用可接受；原文不进日志；设置页隐私提示 | P1 |
| 12 | 附件 `original-{ts}.md` 长期累积 | 随会话清空删除 `attachments/`（决策 4） | P1 |
| 13 | 粘贴代码 | 自动跳过，原样上云（显式可整理结构说明） | P0 |
| 14 | 粘贴链接 / 本地路径（纯指针） | 跳过整理，原样上云，云端 `read_file` / `web_fetch` 处理 | P0 |
| 15 | 长文本夹带链接 / 路径 | 整理但原样保留，prompt 硬性约束 | P1 |
| 16 | 超长 >10k 字 | 分块上限 5 块，其余只进附件 | P1 |
| 17 | 多语言混排 | 保留原文语言 | P2 |
| 18 | 聊天模型就是本地模型（单实例） | `organize()` 与对话串行执行，无冲突 | P2 |
| 19 | 本地模型下载/启动中 | `is_ready()` 为 false → 直接上云 | P0 |
| 20 | 整理失败重试一次（换 prompt 变体） | v2 | P2 |
| 21 | 图片 / 附件输入 | 非文本，天然不整理，走 image 流程 | P2 |
| 22 | 语音转文字无标点长文本 | 无需特判，整理对其特别有效（去口水话） | P2 |
| 23 | 富文本粘贴（HTML 样式） | 前端清洗为纯文本（前端职责） | P2 |
| 24 | **大段粘贴走附件通道**（`paste-*.txt`，question 只有"帮我整理"） | `maybe_preprocess_attachment()`：显式 = 整理指令词 + 附件（附件即指代对象）；自动 = 内容超阈值且非代码/表格；整理版替换附件 content，原文仍是附件自身 | P0 |
| 25 | 重复/退化内容（同一段落 ×N） | 模型输出「无法整理」→ 校验拒绝 → 原样上云（合法拒绝，不是 bug） | P2 |

**已确认决策（按推荐值）**：

1. 显式触发：指令词 + 文本指代词双命中才触发（防"帮我整理房间"误触发）；
2. 自动触发：默认开（`local_llm_preprocess_auto=true`），前端必须提示"已自动整理"；
3. 后续轮次：云端默认不把原文注入上下文，靠附件按需读取；
4. 附件清理：随会话清空删除 `attachments/`。

## 9. 验收用例

1. 粘贴 3000 字会议纪要 → 自动整理出「主题分段 + 要点 + 待办」，云端基于整理版回答，附件可查原文；
2. 发送"帮我整理这段：…"（短文本）→ 显式触发；
3. 发送"帮我整理房间的计划" → **不**触发整理，原样上云（决策 1）；
4. 粘贴一段代码 → 不自动整理，原样上云；
5. 粘贴一张 CSV 表格 → 不自动整理，原样上云；
6. 停止本地模型后粘贴长文 → 原样上云，无报错、不卡顿；
7. 构造 organize 失败（模型不可用 / 输出校验不过）→ 原样上云，消息不丢；
8. 粘贴 12000 字文档 → 前 5 块整理 + 附件保留全文，云端回答不跑偏；
9. 会话清空后 `attachments/` 目录被删除（决策 4）。

## 10. 后续演进（v2）

- 定时任务路径接入预处理；
- **路径/链接 + 整理指令**：用户发"整理一下 /Users/.../report.md"时，本地先读文件（走现有 `read_file`/`document_reader` 权限边界）再整理，而非把路径当指针跳过——需单独设计文件读取授权；
- 整理失败重试一次（换 prompt 变体）；
- 整理质量离线评估：抽样比对"仅原文上云" vs "整理版上云"的云端回答质量与 token 消耗；
- 若评估显示整理版明显优于原文上云，将 `organize()` 加入微调候选（LoRA），与意图分类共用数据闭环。
