# 事故回流最小落地设计

> 目标：把 `tool_runs` 表里的**工具失败记录**回流为新的 agent_todo，形成「失败 → 复盘/修复 → 闭环」。
> 设计原则：**不加新表、不动核心链路、改动收敛在失败落库这一处钩子**。

> ✅ **实施状态：已实现并验证（2026-09-01）**。改动文件见第三节改动清单；新增测试 `tests/test_recovery_loop.py` 6 条用例全绿，相关回归 90 passed，全量套件通过。

---

## 一、现状断点（为什么缺）

代码证据：

- `db/tool_runs.py:48` `add_tool_run` 完整落库每次工具调用（含 `status='error'`）→ **事故数据已采集**。
- `agent/state/plans.py:38` `_finish_todo(todo, False, msg)` 把 todo 置为 `error` 后**直接返回，没有下一步动作** → **数据没被喂回系统**。
- `agent/tools/execution.py:987-1004` 是唯一的失败收敛点：工具成功/异常都在这里 `_finish_todo`。

断点就一句话：**采集了事故，却没有回流动作。** 缺的不是表，是那一个函数调用。

## 二、设计：三行钩子 + 一个函数

### 新增函数 `agent/state/plans.py`

```python
def _spawn_recovery_todo(
    session_id: str,
    todos: list[dict[str, Any]],
    failed: dict[str, Any],
    reason: str,
) -> dict[str, Any] | None:
    """失败回流：把一次工具失败转成一条『复盘/修复』todo 挂回当前计划。

    - 同类去重：同一 tool + 同一根因只回流一次（防死循环 / 防刷屏）。
    - 全局上限：同 session 的复盘项总量封顶，超限停止再造（防
      "多种工具连环失败 → 待办无限累积 → token 被逐个试光"）。
    - 复用 agent_todos 表，`index` 追加到末尾，状态置 pending。
    - 返回新 todo；被去重或超上限时返回 None（不重复造）。
    """
    for t in todos:
        if t["status"] == "pending" and _is_recovery_title(t["title"], failed["tool_name"]):
            return None
    if _count_recovery(todos) >= _MAX_RECOVERY_TODOS:
        return None
    title = f"[复盘] {failed['tool_name']} 失败：{reason[:40]}"
    new = db.add_todo(session_id, title)          # 新表? 否——复用 add 逻辑
    return new

# 同 session 复盘项总量上限：超过即不再回流，改为收敛给用户提示。
_MAX_RECOVERY_TODOS = 5

def _is_recovery_title(title: str, tool_name: str) -> bool:
    return title.startswith("[复盘]") and tool_name in title

def _count_recovery(todos: list[dict[str, Any]]) -> int:
    return sum(1 for t in todos if t["title"].startswith("[复盘]"))
```

`db/todos.py` 只需新增一行复用 `replace_todos` 同构的 `add_todo`：

```python
def add_todo(session_id: str, title: str) -> dict[str, Any]:
    now = _now()
    index = len(list_todos(session_id))          # 追加到末尾
    with get_conn() as conn:
        conn.execute(
            "INSERT INTO agent_todos "
            "(id, session_id, \"index\", title, status, result, created_at, updated_at) "
            "VALUES (?, ?, ?, ?, 'pending', NULL, ?, ?)",
            (_new_id(), session_id, index, title, now, now),
        )
        conn.commit()
    return list_todos(session_id)[-1]
```

## 四、防死循环 / 防刷屏 / 防烧 token（关键护栏）

事故回流最容易翻车的是**无限循环**、**刷屏**和**token 被反复试错烧光**。双闸四护栏：

1. **同类去重**：`_spawn_recovery_todo` 先查是否已有同 tool 的 pending 复盘项，有则跳过——同一工具失败 100 次也只造 1 条。
2. **全局上限（双闸第二道）**：同 session 的复盘项总量封顶 `_MAX_RECOVERY_TODOS = 5`，超限即停止回流。这兜住"多种工具连环失败 → 待办无限累积"的软肋——虽然每个工具只 1 条，但 10 个工具就是 10 条，agent 可能逐个试，token 仍会被慢慢烧。超限后不再造新复盘项，收敛为一次性提示用户"连续失败，建议换个思路"。
3. **不自动执行**：回流只**追加 todo**，不自动重新执行工具——执行权仍交给 agent 的下一轮决策，避免无人监督的重试。
4. **成本上限**：复盘 todo 与普通 todo 同表同权，`_claim_next_todo` 会认领它；但建议在 plan 注入 prompt 时提示「复盘项是辅助项，不阻塞主流程」（可选，非必须）。

> 一句话：**去重封死"同工具的循环"，总量上限封死"多工具的累积"，不自动执行保证"每一步重试都在用户眼皮底下"。** token 燃烧路径上始终有人类刹车。

## 六、边界与取舍

- **为何复用 agent_todos 而非新表**：复盘本质上就是一条"待办"，新表会割裂 todo 状态机（认领/完成/进度都要二套逻辑）。用前缀 `[复盘]` 做语义区分足够，查询可 `LIKE '[复盘]%'`。
- **为何不加自动重试**：自动重试属于"无人监督的执行"，与项目安全模型（工具执行要经过 approval）冲突。回流为 todo 后由 agent 决策，天然受审批约束。
- **上限阈值为何是 5**：纯保守取值。复盘项太少会漏掉真实问题（比如 3 个不同根因就占满），太多则退化成刷屏。若想更精确，可按 session 的工具总失败次数设比例（如 20%），但会增加复杂度，先不做。
- **超限后的表现**：停止回流，不再追加复盘项；agent 端提示"连续失败已超过 N 次，建议拆解任务或换一种思路"，把选择权交回用户。
- **后续增强（不在本次范围）**：跨 session 的事故统计 → 沉淀进 `user_memories`，形成"组织记忆"；这对应方案文档「防止复发 → 新 intent」的完整形态。

## 七、一句话总结

把 `tool_runs` 里已有的 `error`，在 `_finish_todo` 失败落库后**追加成一条 `[复盘]` todo** —— 30 行、无新表，就把「采集失败数据」升级为「从失败中学习」的闭环，补上方案文档里那根唯一的回箭头。

## 八、附录：token 安全论证（为什么不会烧光）

沿"一条失败记录从产生到结束"的完整生命周期，逐环节核算：

| 环节 | 是否耗 token | 说明 |
|------|-------------|------|
| 失败 → 追加 `[复盘]` todo | **否** | 纯一次 SQL INSERT，零模型调用 |
| 复盘项躺在表里等待认领 | **否** | 不执行就不耗 token，只是表里一行数据 |
| agent 认领复盘项 | 是（一次） | 与普通 todo 同价：一次决策 ≈ 一次普通工具调用 |
| 认领后再次失败 | 是（一次） | 触发回流 → 被**同类去重**拦截，不再新增 |
| 多种工具连环失败 | 是（逐个） | 被**总量上限 5** 拦截，最多累积 5 条待办 |
| 自动重试同一工具 | — | **不存在**：回流从不触发执行，重试必走 agent 决策 + 用户审批 |

结论：**单次失败的边际成本 = 0（写一条待办）+ 最多 1 次认领决策；最坏情况（连环失败）被 5 条上限封顶后收敛为提示。** 由于重试永远要过审批，用户是 token 消耗的最后一道、也是最硬的一道闸。
