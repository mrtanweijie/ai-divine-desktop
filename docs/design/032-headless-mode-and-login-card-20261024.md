# 无头模式与登录卡片设计（032）

> 日期：2026-10-24
> 依赖：031 通用 Web 任务执行引擎
> 状态：**设计文档** — 不含任何实施承诺

---

## 1. 背景与动机

031 的执行环境是**有头**专用浏览器：每次任务都弹窗口打扰用户，页面看不懂时靠截图识别（caption），体验一般。用户诉求：

1. **默认无头执行**——不打开可见浏览器；
2. 登录/校验尽量自动化：登录卡片收集**手机号 + 短信验证码**自动填写；**图形验证码自动识别**完成填写后继续流程；
3. **降级链**：只有无法自动通过的人机校验（滑块/扫码/反复失败），才降级到当前方案——打开浏览器让用户手动操作。

## 2. 模式设计

新增设置 `browser_mode`：`headless`（默认）/ `headed` / `auto`。

| 模式 | 行为 |
|------|------|
| `headless` | 全程无窗口（`--headless=new`），日志与时间线是唯一观测面 |
| `headed` | 现状：有头专用浏览器（调试/风控敏感场景） |
| `auto` | 常规操作 headless；命中交互屏障且自动手段失败 → 切有头浮窗，完成后切回 |

- **同一专用 profile**：登录态持久，headless 与有头共享；Chrome 不允许同 profile 双实例，模式切换 = 杀旧实例 + 重启 + 从断点 URL 重新导航（断点续跑依赖 write_todos，已有）；
- 技术事实：`--headless=new` 与有头的 DOM/CDP 能力一致，`browser_click/fill/snapshot/extract` 全部照常；差异在**风控指纹**（见 §6）；
- 引导启动函数参数化：`launch_debug_chrome(force, headless)`；端点文件不变，通道自愈逻辑复用。

## 3. 校验处理降级链（核心）

每个交互屏障按序尝试，**失败才降下一层**：

```
L0  已登录（专用 profile 持久会话）→ 直接继续
L1  自动登录表单：检测「手机号+验证码」登录表单
    → 登录卡片收集手机号/短信码（用户从短信抄录）→ 受控填入 → 自动提交
L2  图形验证码：验证码元素截图 → GLM-4V 识别 → 受控填入 → 重试 ≤2 次
L3  回到 L1（短信重发 / 换一题重识别）
L4  降级：切有头浮窗（031 现方案）——滑块、扫码、L1-L3 两次失败才走到这里
L5  全部失败：停止并汇报
```

- **短信验证码无法"自动识别"**（在用户手机上）——卡片回传是唯一路径；
- **图形验证码可以自动识别**——复用 `browser_read_page` 的视觉链路（元素截图 → GLM-4V，prompt 换为识别字符），识别失败降级为卡片人工认读；
- **滑块/行为验证码不自动拖拽**（风控 + 成功率差）——直接降级 L4。

## 4. 登录卡片（复用 A2UI）

- 卡片 = `render_ui` 面板：站点域名、手机号输入框、验证码输入框、[获取验证码] [确认登录] 按钮；
- 按钮动作经 A2UI 回流到主 agent → 主 agent 委派 `web_task(confirmed=true, 受控登录填入)`：
  - 填手机号 → 点「获取验证码」→（用户收短信、填码）→ 填验证码 → 点登录；
- **受控填入**（新引擎操作 `op_login_fill`）：
  - 域名校验：只允许填**当前任务目标域名**的页面；
  - 字段白名单：只允许填手机号（`type=tel`）与验证码（`autocomplete=one-time-code` / 名称含验证码）字段；
  - **密码字段永远拒绝**——用短信登录形态规避密码；
- 图形验证码识别失败时，卡片追加验证码截图 + 人工输入框。

## 5. 安全边界修订（对 031 §6 的定向豁免）

| 项 | 031 原边界 | 032 修订 |
|----|-----------|---------|
| 短信验证码输入 | 进入即停 | **定向豁免**：用户经卡片主动提供 + 仅任务目标域名 + 仅登录表单字段 |
| 图形验证码 | 进入即停 | **定向豁免**：自动识别 ≤2 次，失败转人工 |
| 滑块/扫码 | 进入即停 | 不变（降级浮窗人工） |
| 密码输入 | 永不 | **不变**（短信登录规避） |
| 支付 | 永久人工 | **不变** |

- agent **不得自主决定**输入凭据——填入必须由用户卡片动作触发；
- 隐私：手机号/验证码仅用于本次填写，不进记忆、不落日志（log 脱敏）。

## 6. 风险

1. **headless 指纹风控**：美团/饿了么有设备指纹，无头特征（navigator.webdriver、WebGL）更易被识别——缓解：`--disable-blink-features=AutomationControlled` + 真实 UA + 固定 profile；**下单/支付段建议有头**（auto 模式策略）；
2. **图形码识别率**：GLM-4V 对扭曲字符识别率中等，失败即降人工，不重试刷站；
3. **模式切换丢页面状态**：断点重导航兜底；
4. **验证码自动化的 ToS 敏感性**：频次护栏（`shopping_daily_actions_cap`）覆盖登录尝试次数。

## 7. 分期

> 实施状态（2026-10-24）：**A/B/C/D 全部已实现**——`browser_mode` 设置与模式失配
> 自动切换、登录屏障检测（login_barrier）、验证码分级豁免（密码永拒 / 验证码
> confirmed 段放行）、`browser_read_captcha` 视觉识别、按委派段 headless 覆盖
> 降级有头、断点重导航、设置页模式切换与策略编辑。A2UI 富版登录卡由模型经
> render_ui 组合（提示词引导），无专属代码。

| 阶段 | 内容 |
|------|------|
| A | `browser_mode` 设置 + launch 参数化（headless/headed 切换）+ 现有 e2e 无头回归 |
| B | 交互屏障检测（登录表单启发式）+ 登录卡片（A2UI）+ `op_login_fill` 受控填入 |
| C | 图形验证码识别（元素截图 → vision → 填写，失败降卡片） |
| D | 降级浮窗切换（同 profile 有头重启 + 断点重导航）+ 滑块人工提示 |

阶段 A 完成即可回答"不打开浏览器跑任务"；B/C 落地登录闭环；D 是完整降级链。
