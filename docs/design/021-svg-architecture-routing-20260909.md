# 021 · SVG 架构图增强：mermaid 优先 + 追问升级（2026-09-09）

> 编号：021 ｜ 类型：design ｜ 日期：2026-09-09 ｜ 状态：已实施（2026-09-09，§4 全部落地，后端 pytest 143 passed）
> 关联：[001-mermaid](../design/001-mermaid-20260811.md)（Mermaid 图基线）、[002-svg-tool](../design/002-svg-tool-20260811.md)（SVG 工具基线）
> 起因：用户观察「只有图标类走 draw_svg，架构图一律落 mermaid」，要求架构图也能走 SVG，且默认出明暗双配色

---

## 0. 一句话结论

**不动意图路由，架构图仍默认输出 mermaid；输出后主动询问用户是否需要 SVG 增强版，确认后走 `draw_svg`，按桌面端当前主题输出一份，末尾附一张换色卡片（8 种配色按场景挑 4 个，见 §4.7）；用户明确要求或经询问确认后才出 dark/light 两份。**

三个必须改的点：

1. **工具裁剪（硬门槛）**：`draw_svg` 当前只挂 `svg` 意图，追问轮若没命中 `svg` 就拿不到工具——放宽为 `("svg", "mermaid")`。
2. **主题感知（新链路，前置依赖）**：默认只出一份，前提是后端得知道桌面端当前是 dark 还是 light。**这条链路目前不存在**（见 §4.5），是本次改动中唯一跨前后端的部分。
3. **换色卡片（新增交互）**：出图后询问是否换配色，预置 8 种方案、每次挑 4 个（见 §4.7）。

## 2. 技术验证：单文件主题自适应不可行（resvg 实测）

用项目 `svg_to_png.py`（resvg_py 第一级命中）实测三种写法，采样背景像素：

| 写法 | 渲染结果 | 结论 |
|---|---|---|
| `<style>:root{--bg:#fff}</style>` + `fill="var(--bg)"` | `#000000` a=255 | ❌ **`var()` 不解析**，fill 回落 SVG 默认黑色，坑很隐蔽 |
| `<style>.bg{fill:#0b0d0f}</style>` + `class="bg"` | `#0B0D0F` | ✅ class 选择器正常 |
| `.bg{fill:#fff}` + `@media (prefers-color-scheme:dark){.bg{fill:#0b0d0f}}` | `#FFFFFF` | ⚠️ 语法能解析，但 resvg **恒取 light 分支**（无系统主题概念） |

**结论**：单文件自适应方案在浏览器预览能用，但 PNG 导出必坏（全黑或恒亮）。
**必须生成 dark / light 两份定色 SVG。**

## 3. 策略决策：mermaid 优先 + 追问升级（2026-09-09 用户定）

**不改意图路由**。"架构图"仍归 mermaid（`intent.py:206` 不动），首轮照旧正文输出 mermaid 代码块。

**改的是收尾动作**：架构类图输出后追加一次询问，用户确认才升级 SVG。

| 维度 | 取值 | 理由 |
|---|---|---|
| 首轮 | mermaid 代码块 | 快、省 token、可编辑、前端已渲染 |
| 收尾 | options 卡片询问"是否需要 SVG 增强版" | 把选择权交给用户，避免每次都付 SVG 成本 |
| 确认后 | `draw_svg` 出 dark/light 两份 | 定色两份，见 §2 实测 |

这个策略对意图层是**零改动**，风险最低。

## 4. 改造清单（6 处）

其中 4.1–4.4、4.6 都在后端 prompt / 工具层，属小改；**4.5 是唯一跨前后端的新链路**。

### 4.1 工具层 —— 唯一必须改的硬门槛

`app/agent/tools/tools.py:62-68`：

```python
"draw_svg": ("svg", "mermaid"),   # 原为 "svg"
```

**为什么必须改**：意图回补机制（`intent.py:308` `_TOOL_TO_INTENT`）依赖"上一轮实际调用过某工具"，但首轮走 mermaid 是**正文输出、不调任何工具**——没有回补信号。追问轮用户若只回"好"，意图大概率仍是 `mermaid`，`draw_svg` 会被裁掉，模型只能干瞪眼。

放宽为双意图后，`svg` 或 `mermaid` 任一命中即注入。与 `pdf_generate: ("pdf","resume","html")` 的既有保守原则一致（同文件 L48-50 注释已写明短追问场景的坑）。

`edit_svg` / `svg_to_png` 不必放宽：确认后一旦调过 `draw_svg`，后续轮由 `_TOOL_TO_INTENT` 回补 `svg` 意图即可拿到。

**注意**：`draw_svg` **不需要加 theme/palette 参数**——配色写死在 SVG 源码里，工具只负责落盘，加参数只是徒增复杂度。

### 4.2 规则层 —— mermaid 侧补询问动作

`prompt_sections.py` 的 `_MERMAID_RULES`（L371）末尾追加：

```
输出架构类图（分层架构、部署拓扑、模块关系、系统结构）后，在末尾用 options 卡片询问用户

### 4.3 规则层 —— SVG 侧补架构图绘制规范（关键）

`_SVG_RULES`（L377）末尾追加。**这段才是让 LLM 画得好的关键**——把本次实战踩过的坑全部固化：

```
绘制架构图 / 分层图 / 拓扑图时，除上述规则外还必须遵守：
- 版式：自上而下分层，层间距统一；卡片尺寸一律由容器反推，禁止逐个手写 x 坐标：
  内容区 = 容器宽 − 左右内边距×2；n 张卡等宽时 w = (内容区 − 间距×(n−1)) / n，
  x 依次累加 w+gap。手写坐标极易出现间距 12/1/1 这种粘连且右缘对不齐的问题。
- 间距：同层卡片间距全图统一（推荐 12）；容器左右内边距相等；
  各层首卡左缘、末卡右缘必须对齐同一条竖线。
- 字阶：主标题 12.5 / 副标题 12 / 层标签 10.5，级差 ≥1.5px；字重主 500、副 400 分级；
  中文必须加 letter-spacing 0.2–0.5，否则小字号发闷。
- 层次靠色块不靠线：卡片底与容器底明度差 ΔL ≥ 0.02；边框对比度控制在 1.5–1.7，
  线宽固定 0.5——绝不加粗描边来强调层次（"线显粗"几乎都是色块没拉开导致的）。
- 圆角：容器 14 / 独立卡 10 / 内卡片 6，逐层递减。
- 多行文字行距必须统一，且整块按卡片高度垂直居中，不要凭手感排 y。
- 字体栈必须含 Microsoft YaHei（Windows 回退），项目 UI_FONT 为
  -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", "PingFang SC", sans-serif。
- 每个图层、卡片带语义 id（layer-* / card-* / arrow-*），便于 edit_svg 局部修改。
- 文字对比度 ≥ 4.5（WCAG AA），生成后自查。
```

### 4.4 配色策略 —— 默认透明底 + 边框外壳，标题卡兜底可读性（2026-09-09 四次修订）

追加到 `_SVG_RULES`：

```
架构图配色：
- 默认「透明底 + 边框外壳」：不画填充背景板，只画一条与画布同形的 1px 描边
  （fill="none"、内缩 0.5px、rx 16），色随桌面端主题（dark #454a54 / light #d9dde3）。
  画布内部保持透明（导出 PNG 保留 alpha），自然融入所在表面；边框只界定图的范围。
  可读性由块兜底：所有文字必须坐在块上（标题卡/层容器/内容卡），不得裸放画布。
- 头部主标题与副标题必须包进标题卡——全宽横幅、左右缘与各层对齐、
  底色取容器底、边框取容器边框、rx 14；标题 16px/600、副标题 11px，
  默认卡高 68（上下留白 18/18、行间 10），基线 = 卡顶 + 31 / + 50；
  文字 x = 卡片 x + 20，严禁等于卡片 x。
  标题卡可按用户要求豁免（「标题不要块」），豁免时提醒浅色表面看不清风险，不拒绝执行。
- 仅当用户明确要求「带背景/填充背景」时才画全幅圆角背景板（rx 16 全幅），
  色取主题 bg（dark #0b0d0f / light #f6f7f9），外壳描边随之同形内缩。
- 主题只决定墨水色（文字/卡片/边框），默认一份且匹配系统提示中的「当前桌面端 UI 主题」，
  dark 档配深色壳、light 档配浅色壳；用户说明图的去向时按去向定档（墨水与壳同步换档）。
- 两份（-dark / -light）仅限：① 用户明确要求；② 询问后确认。
- 禁止 var() / @media prefers-color-scheme（见 §2 实测）。
- dark 档：主色取 QUAL_DARK，墨水取 UI_COLORS.dark
  （surface #121517 / text #f2f4f6 / textSecondary #a4adba / textMuted #6f7783）。
- light 档：主色取 QUAL_LIGHT，墨水取 UI_COLORS.light
  （text #1f2937 / textSecondary #5b6472 / textMuted #8a94a3）；
  卡片底禁纯白，用 #eef0f3 并靠边框 + 明度差补层次。
- QUAL_LIGHT 九色：#FACC8F #F3962F #A3D8F4 #EF898E #DD656D #61A7D0 #036EAD #FAAD9D #8798C9
  QUAL_DARK  九色：#A3D8F4 #FAAD9D #FACC8F #EF898E #8798C9 #DD656D #61A7D0 #F3962F #036EAD
  真源：divine-app/src/pages/chat/components/ChartBlock/chartOptions.ts（QUAL_*）
        与 divine-app/src/styles/uiPalette.ts（UI_COLORS）。若本规则与代码冲突，以代码为准。
- 派生用 HSL：dark 档容器底 l≈0.10、卡片底 l≈0.19、边框 l≈0.30、主文字 l≈0.84、次文字 l≈0.68；
  light 档容器底 l≈0.93、卡片底 0.94、边框 0.80、主文字 ≤0.25、次文字 0.42。
- 用户指定配色时，用用户给的色值替换主色，其余派生规则不变。
```

### 4.5 主题感知链路 —— 新增（本次唯一跨前后端改动）

「默认按桌面端主题出一份」的前提是后端知道当前主题。**这条链路目前不存在**。

**现状**：主题只活在前端 —— `divine-app/src/services/theme.ts` 把偏好存 localStorage（`STORAGE_KEYS.theme`，值 `dark`/`light`/`system`），resolved 后写到 `document.documentElement.dataset.theme`。全仓检索确认：`divine-app/src/services/` 下除 `theme.ts` 外无任何地方把主题发出去；`divine-server/app/` 里所有 `theme` 都是 **PDF 版式主题**（`docgen/pdf/theme_manager.py` 等），与 UI 明暗无关。

**照抄 `locale` 这条既有链路即可**（同性质的"前端环境信息"传递，5 个环节）：

| 环节 | `locale`（既有） | `ui_theme`（新增） |
|---|---|---|
| 请求体 | `app/schemas.py:26` | 同文件加可选字段 |
| 接口接收 | `app/api/chat.py:116` 解析、L625 传入 ctx | 同处解析并传入 ctx（非法值回落 `dark`） |
| 上下文 | `app/agent/core/context.py:44` | 加字段，默认 `dark` |
| Prompt 注入 | `app/agent/core/prompts.py:437` `language_instruction(ctx.locale)` | 加一行环境说明 |
| 前端发送 | `pages/chat/hooks/useChatStream.ts:393` | **同两处都要加**（L393 主请求 + L490 retry） |

两个易错点：

- **retry 路径（L490）也要加**，否则用户点「重答」时主题丢失、回落到默认值。
- **前端要传 resolved 值，不是 preference** —— `system` 必须先经 `resolveTheme()` 解析成 `dark`/`light` 再发，后端不认 `system`。用 `services/theme.ts` 的 `useTheme()` 直接拿。

**已知局限（需接受）**：SVG 是定色静态文件，生成后**不随用户切主题而变化**，切了要重新生成。mermaid 无此问题（前端渲染、天然跟随主题）——这也是「默认 mermaid」的又一理由。

### 4.7 配色方案库（8 种）+ 生成后换色询问

**交互范式照抄 PDF 旅行手册主题色卡片**（`prompt_sections.py:184` `_PDF_TRAVEL_RULES`）：预置 N 种方案 → 每次按场景挑 4 个出 `options` 卡片 → `other: true` 兜底自定义。

**流程**：按当前明暗主题输出 SVG 后，在正文末尾附一张换色卡片；用户点击/回复即换配色；用户未选择则到此为止，**不追问第二次**。

**换色执行**：用 `edit_svg` 传完整新源码，**图层结构、坐标、尺寸、文案一律不动，只替换色值**。不要因为换色重画版式。

**8 种配色方案**（色值全部取自项目色板 —— QUAL 九色 + 语义色，与图表同源）：

| # | 方案 | key | 色相序列（按层自上而下取用，层多则循环） | 适用场景 |
|---|---|---|---|---|
| 1 | 科技蓝 | `techblue` | `#036EAD` → `#61A7D0` → `#A3D8F4` | **默认**，系统 / 前端分层架构 |

| 5 | 晨雾青 | `mistcyan` | `#A3D8F4` → `#2F9E6E` → `#61A7D0` | 基础设施 / 部署拓扑 / 运维 |

## 6. 实施后的验证方式

用同一句话（"画一张墨客 Studio 的前端分层架构图"）跑，检查：

1. 首轮是否输出 mermaid 代码块，且末尾出现 options 询问卡片；
2. 回复"要 SVG 版"后，`draw_svg` 是否被注入并被调用（工具裁剪是否放行）；
3. **是否只产出一份**，且配色匹配桌面端当前主题：分别在 dark / light 主题下各跑一次，两次产物应分别是 dark 档 / light 档——**切主题后产物必须跟着变**，否则说明 §4.5 链路没生效（只是恰好撞上默认值）；
4. 明确说「明暗各来一份」后，是否产出 `-dark` / `-light` 两个文件；
5. 用 `svg_to_png.py` 渲染采样，底色应接近 `#0b0d0f`（dark）或 `#f6f7f9`（light）。**若出现 `#000000` 说明 `var()` 未解析**，见 §2；
6. 按 §4.3 规范复核：卡片间距各间隙相等、各层左右缘对齐、文字对比度 ≥4.5；
7. **换色卡片**：末尾是否出现 options 卡片，恰好 4 个选项 + `other:true`，且不含当前配色；
8. **换色执行**：点击某个配色后是否走 `edit_svg`，且**只有颜色行变化**——对新旧 SVG 做 diff，除 `fill`/`stroke` 外不应有任何坐标或尺寸改动。

## 7. 附：本次实战沉淀的三个教训

已在会话内实测，写进规则是因为它们都是"照抄坐标/凭手感"导致的返工。

1. **坐标不能照抄输入 SVG**。原始素材自带 `60/203/335/467` 的错误坐标，间距 12/1/1 且右缘 598（其他层 620），前两版改配色/字阶时未核算，一直在错误地基上装修。**接手外部 SVG 第一步应是核算栅格**。
2. **"线显粗"几乎都是色块没拉开**。卡片底与容器底 ΔL 仅 0.013 时，层次只能靠边框勾，边框被迫成为视觉主角。改 stroke-width 无效，应提亮卡片底、压暗容器底。
3. **像素验证要避开文字行**。扫描卡片区段时若取样行穿过文字，底色被文字像素切断，会测出成片假区段（本次误测出 10 个）。取样应选文字之间的空白行。
