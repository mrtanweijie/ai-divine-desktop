00

一句话结论

X6 真正的产品价值是一台通用图渲染机——只要输入是「节点 + 边 + 语义」，它就能渲染流程图、DAG、状态机、组织架构、思维导图、拓扑、ER、泳道、知识图谱、类图、鱼骨、时间线。

核心架构决策

把「画什么」和「怎么画」彻底拆开。Agent 只输出 kind（场景名）+ 拓扑 + 语义意图；布局引擎、节点形态、连线路由、交互等级、动效策略全部收敛到前端一张 ScenarioPreset 常量表。加一个新场景 = 表里加一行，不改 schema、不改后端、不改渲染器。

① IR 场景无关

IR 里不出现写死的 direction / shape / flow 三件套。图谱结构只有 nodes / edges / groups / meta，场景差异外置到 Preset。

② Preset 驱动

15 个场景各一行配置：布局引擎 + 参数、节点族、边族、容器族、交互等级、动效、规模上限、视口策略。前端常量，不需要 LLM 参与。

③ 交互分级

L0 静态 / L1 探索 / L2 流动 / L3 编排。场景决定等级，等级决定加载哪些 X6 插件——避免所有图都背上拖拽编辑器的一整套成本。

明确不做的（避免过度设计）

L3 在线编排（拖拽建边、编辑标签、撤销重做）首期不做。它是另一个产品（画布编辑器），与「AI 生成图给人看」是两件事。X6 支持 ≠ 我们应该做。
时序图 / 甘特图 / 纯数据图表不进本链路——Mermaid 与 ECharts 已有成熟解，重复建设只会让渲染体系从 2 套变 3 套。

01

架构：GraphIR + Preset Resolver

IR 渲染链路的核心是 Preset Resolver。它是整套方案里唯一知道「场景」的模块，其余全部场景无关。

// 后端 divine-server
Agent (LangGraph)
  └─ 工具 render_graph            唯一图形渲染工具入口
       ├─ 入参：GraphIR（JSON Schema 校验，kind 是唯一场景字段）
       └─ 出参：完整 GraphIR（JSON）→ 作为 tool 结果持久化并经 SSE tool 事件下发
             前端展开为入场事件（set_meta / add_node / add_group / add_edge / done）节流播放

// 前端 divine-app · src/pages/chat/components/GraphBlock/
GraphIR.ts            // 类型 + 白名单校验（IR 来自 LLM，按不可信输入处理）
presets/
  index.ts            // ScenarioPreset 表：kind → 布局/形态/交互/动效
  layout.ts           // 布局引擎映射：dagre | elk | compactBox | mindmap | force | 自定义
shapes/
  registry.ts         // 节点形态注册表（纯 SVG markup，可导出）
  edges.ts            // 边族：orth | curve | straight | selfLoop
GraphRenderer.ts      // 场景无关：IR × Preset → X6 渲染
RenderScheduler.ts    // 80ms 批处理
AnimationManager.ts   // 动画池 + 视口外暂停
GraphToolbar.tsx      // 按 Preset.capabilities 渲染按钮
GraphInspector.tsx    // 节点/边详情面板

Preset Resolver 的解析顺序

kind ──► PRESETS[kind] ──► {
            layout:  { engine, opts },      // 布局引擎 + 参数
            shapes:  NodeFamily,            // 节点形态族
            edges:   EdgeFamily,            // 边族 + 路由
            groups:  GroupFamily | null,    // lane / cluster / combo
            level:   'L0'|'L1'|'L2',        // 交互等级 → 决定加载哪些插件
            motion:  MotionSpec,            // 入场 / 流动 / 播放
            limit:   { nodes, edges },      // 规模上限
            view:    'fit' | 'center' | 'scroll',
            capabilities: ['export','flow','play','fold','minimap']
         }

关键约束：kind 必须是封闭枚举。LLM 输出未知 kind → 后端校验拒绝并结构化报错让 Agent 自纠（与 source/target 引用校验同一机制），不要静默 fallback 到 flowchart——静默降级会让错误形态被当成正确结果固化下来。

02

GraphIR 规范

GraphIR 的字段设计：不含 direction、shape、flow（全部下沉到 Preset）；增 kind、groups、节点 role、边 kind。

{
  "kind": "flow",                        // 唯一场景字段，封闭枚举，见 §3
  "meta": { "title": "订单支付链路", "summary": "…" },
  "nodes": [
    { "id": "start", "label": "提交订单",
      "role": "start",                    // start|end|process|decision|data|entity|state|group_root|milestone
      "tone": "info",                       // success|warning|error|info|neutral
      "lane": "order",                     // 泳道归属（kind=swimlane 时必填）
      "parent": "g1",                      // 层次归属（org/mindmap 可选，冗余于边）
      "note": "点击节点查看的详情",
      "badge": "P0" }                       // 右上角小标，可选
  ],
  "edges": [
    { "id": "e1", "source": "start", "target": "stock",
      "label": "校验",
      "kind": "flow",                      // flow|dep|transit|inherit|assoc|contain
      "tone": "info",
      "style": "solid",                     // solid|dashed
      "flow": { "mode": "antline", "speed": 1 } }  // 可选，仅 L2 场景生效
  ],
  "groups": [                              // 容器：泳道 / 集群 / 分组
    { "id": "g1", "label": "接入层", "type": "cluster", "members": ["cdn","waf","gw"] }
  ],
  "demoPath": ["start", "stock", "pay"]     // 可选，节奏由前端编排
}

字段约束（后端强校验）

字段规则理由
kind封闭枚举 15 项，未知即拒绝防止 LLM 发明场景导致 Preset 缺失
role封闭枚举；Preset 决定 role → shape 的映射Agent 说「这是什么角色」，不指定长什么样
tone5 档语义色名，禁止色值主题切换与对比度由前端统一兜底
lane / parent必须指向已声明的 group / node层次与泳道是结构，不能靠坐标表达
flow仅 mode: antline|pulse、speed: 0.5|1|2守住「不算时序」原则
坐标禁止任何 x/y/w/h 字段布局是前端职责
规模nodes ≤ Preset.limit.nodes，超限结构化报错不同场景上限不同（见 §3）

安全：白名单校验、拒绝 __proto__ / on* / 任意 attrs 注入。新增的是 kind 与 role 也必须白名单，否则 LLM 可以借 role 名注入形态。

场景画廊 · 16 个真实渲染样板

4.1　DAG 自定义节点 · 对照 X6 showcase dag / dataProcessingDag

通用矩形节点在 DAG 场景里信息密度太低——看不出「跑到哪一步」「这步是干嘛的」。X6 官方这两个 showcase 用自定义富节点解决：节点内嵌类型图标 + 标题 + 状态徽标。这里把它适配到 Divine 的设计体系。

  • dag-node　任务编排型（对应 X6 dag 的 AlgoNode）
  • ① 类型图标 16×16，距左 16px，stroke 描边不吃 tone 色
  • ② 标题 12.5px，距左 36px，超长省略号截断
  • ③ 状态徽标 14×14，距右 16px
  • ④ 端口 r 3.4，TB 布局时在上/下
  • dp-node　数据加工型（对应 X6 dataProcessingDag）
  • ① 类型图标放 28×28 圆角色块（rx 7）内，色块用 surface-2
  • ② 加工类型枚举：INPUT / FILTER / JOIN / UNION / AGG / OUTPUT
  • ③ 标题距左 62px，状态距右 18px
  • ④ 端口在左/右（in / out），与 LR 布局一致

状态徽标（4 态）

类型图标（全部内联 path，不外链图片）

与 X6 原版的取舍：三处必须改

① 不用 React/HTML 节点。X6 这两个示例都用 @antv/x6-react-shape 注册组件节点（渲染进 foreignObject）。但 foreignObject 在 WKWebView 下 toPNG 极易失败、且样式是外联 CSS，导出即丢——与「导出 PNG/SVG 是硬需求」直接冲突。改用等价的纯 SVG markup，导出链路与现有节点完全一致。
② 图标全部内联 path，禁止外链图片。官方示例用的是 gw.alipayobjects.com 外链图。我们是本地优先 + 隐私可控，外链既泄隐私又会在导出后失效。
③ 砍掉编辑器交互。官方示例的「+ 添加下游节点」下拉菜单、节点「更多操作」菜单、antd Tooltip / Dropdown 都是 L3 画布编辑器能力，首期不做（见 §6）。

4.3　系统架构图 · arch-node / boundaries / legend

架构图是第 14 个 kind（arch）。三块能力：arch-node（类型图标瓦片 + 名称 + 技术栈副行 + 徽标，176×52）、boundaries（region / security-group 平面列表，按面积降序重叠绘制——大框套小框即嵌套视觉，不做递归分组）、legend（实体类型图标 + 边线型图例区画在画布底部，随 toSVG 导出带走）。画廊中的样例即典型三层 Web 栈：边缘交付 → 安全组内的网关与服务 → 缓存 / 主库 / 队列 / 后台任务。

三个边界约束

① 禁绝对坐标。布局交给引擎（boundary 就近约束是否可用 compound 布局进 P0 验证，退路是分区域布局后拼接）；② 包裹深度 ≤ 2（region 内套 security-group 即到顶，校验拒绝更深嵌套）；③ type 六类封闭枚举 external / security / cloud / backend / database / messagebus，图标全部内联 path、禁止 URL。边线型语义：实线=同步调用 / 虚线=异步消息 / 点线=数据复制，协议文本放边 label。

Preset / IR 侧的变化

项决定理由
kind拆为 dag（任务编排）+ dataflow（数据加工）两个节点形态与信息密度差异足够大，各自一行 Preset 比塞进一个 kind 加开关更清晰
node.state新增场景特有可选字段：pending | running | success | failedPreset 可声明自己支持哪些额外字段，这是 Preset 架构的应有之义；其他场景忽略即可
tone 关系state 映射到 tone（running→info、success→success、failed→error、pending→neutral）不引入第二套语义色；不改通用设计层定稿的「neutral≡info 不上色」原则
node.icon封闭枚举（8 个任务图标 / 6 个加工类型），禁止 URL白名单校验，防 LLM 注入外链资源

4.2　状态机 / 组织树 / 思维导图 / 知识图谱 · 四类富节点

这四个场景的通用节点是最撑不住的：状态机看不出初态终态、组织树没有身份信息、思维导图分不清层级、知识图谱既挤又无类型。下面四类各自解决一个具体的信息缺口。

  • ② 状态名距左 18px，超长省略号
  • ③ 右侧时限徽标（badge），如 30m
  • ④ active 态：外扩 4px 脉冲环，2.2s 循环
  • org-node 176×56　组织树节点
  • ① 头像 36×36 圆角 10，取首字（禁外链头像图）
  • ② 姓名 12.5px + ③ 职位/编制 10.5px 双行
  • ④ 下边缘折叠角标 = 直属子节点数
  • 头像首字比图片更稳：无外链、无 404、导出不丢
  • map-root 140×46 / branch 118×34 / leaf 三级
  • ① root 描边加粗至 2px，标题 13.5px/600
  • ② branch 左侧 3.5px 分支色竖条
  • ③ leaf 退化为「文字 + 2px 底线」（挂在线上）
  • 三级形态差异 = 层级，不用颜色也读得懂
  • concept-node　圆直径 36–56，按度定尺寸
  • ① 圆内只放类型图标，不放文字
  • ② 名称外置到圆下方 10.5px
  • ③ hub 节点（≥52px）名称加粗提亮
  • 三条信息各占一个通道：大小=重要性、图标=类型、文字=名称

图例：伪状态 · 分支色 · 实体类型 · 边线型

四个设计判断（都不是照抄示例，是取舍）

① 分支色只染「结构性元素」，不染节点本体。思维导图天然需要分支配色，但直接给节点上色会破掉极简黑白体系。所以分支色只出现在连线和左侧竖条上，节点本体保持中性灰描边——分支识别力不减，黑白基底不动。
② 知识图谱圆内不写字。原来把「LangGraph」塞进 78px 圆里，字被压到 10px 还换行。真实图谱的做法是圆点 + 外置标签，圆只承载「大小（度）」和「类型（图标）」两个通道，名称放外面。
③ 状态机补上伪状态。UML 里圆形是伪状态专用（初态/终态），普通状态必须是圆角矩形——原来全用 circle 是语义错的。初态实心圆、终态同心圆、choice 菱形。
④ 组织树头像用首字而非图片。外链头像既泄隐私又会在导出后失效，和「本地优先 + 可导出」两条硬约束冲突。

Preset / IR 侧的变化

场景新增字段约束理由
statenode.active · node.badge · node.pseudopseudo ∈ initial|final|choice；active 全图最多 1 个激活态是「当前在哪一步」，是状态机最常被问的信息
state边标签支持 事件[守卫]守卫段渲染为等宽淡色 tspan，由前端解析UML 迁移标准写法，LLM 本来就会这么输出

05

通用设计层（跨场景同源）

场景可以千变万化，但这四层必须全局一致——否则 15 个场景就是 15 套视觉，比现在的 2 套渲染体系更糟。

节点形态族

按 role 映射，Preset 可覆盖。全部纯 SVG markup，禁用 HTML 节点——HTML 节点无法被 toSVG/toPNG 导出，而导出是硬需求。

统一三层结构：body（底 + 描边）→ tint（语义微染 10%）→ label（文本）。换形态不换配色逻辑。

边族

口径定稿：静态底线 + 流动层双层叠加。底线讲拓扑，流动层讲动态，职责分离后可关、可导、可回放。

floworth 圆角折线 + 实心箭头flow / dag / swimlane

线宽 1.25（选中 1.75）；流动层 dasharray 6 7，speed 0.5/1/2 → 2.2s / 1.1s / 0.58s 循环。

语义 tone（定稿）

neutral 与 info 视觉等同（中性灰描边），只有 success / warning / error 上语义色。默认态是干净的黑白图，异常节点才跳出来——这样语义反而更强，也不会把极简黑白体系染成「彩色流程图」。

dark 档 info = #61A7D0（不复用图表色 #036EAD，暗底 1px 描边不可见）。建议单独建 graphTones.ts，不复用 chartOptions.ts。

容器族（group）

  • lane：横向泳道带，标签左置，底色 1.6% 中性
  • cluster：虚线圆角包围盒，标签左上，底色 2.2%
  • combo：可折叠分组（org / mindmap），首期用「折叠角标」替代真 combo
06

交互分级 L0–L3

等级由 Preset 决定，直接决定加载哪些 X6 插件——避免一张静态 ER 图也背上 Selection + Transform + History 一整套。

Lv能力加载的 X6 插件适用 kind
L0渲染 · hover tooltip · 点击详情面板 · 导出—（核心包）er · class · fishbone · timeline
L1L0 + 缩放平移 · hover 关联高亮 · 折叠展开 · minimap（大图）Scroller · Minimaporg · mindmap · topology · concept
L2L1 + 数据流动画 · demoPath 播放 · 工具条Scroller · Minimap · Selectionflow · dag · state · swimlane
L3L2 + 拖拽建边 · 编辑标签 · 撤销重做 · 吸附对齐+ Transform · History · Snapline · Clipboard · Keyboard · Stencil首期不做
为什么 L3 不做

拖拽编辑意味着「AI 生成的图是草稿，用户要自己改」——这与产品定位（AI 直接产出可用结果）冲突，且会引入持久化、冲突合并、撤销栈等一整套问题。X6 支持不等于该做。如果将来确实要，应该是独立的「画布页」而非聊天消息内的组件。

07

动效策略矩阵

定稿节奏（节点 280ms / 边 480ms / stagger 45ms），按场景族微调。所有动画只碰 transform / opacity / stroke-dashoffset。

性能硬约束（通用规则）

① 动画池上限 20，超限直接置终态；② 视口外暂停——antline 是无限循环动画，长会话里滚出视口不暂停会持续吃 CPU，用 IntersectionObserver 统一控制；③ 尊重 prefers-reduced-motion；④ 力导布局结果在 done 后固化坐标，历史回放不再跑力导。

08

能力边界：什么不进这条链路

收敛目标：X6 链路稳定后，把 Mermaid 承担的静态流程图场景迁过来，避免渲染体系永久并行——但必须先写清边界，否则多场景会变成无限扩张。

图形类型归属理由
本文 12 类「节点 + 边」图render_graphX6 原生强项，交互与导出都可控
时序图 sequenceMermaidMermaid 语法成熟、LLM 生成准确率高；X6 需自建生命线版式，投入产出比差
甘特图 ganttMermaid本质是时间刻度条，非拓扑图
类图 classDiagramMermaid（默认） / X6（需交互时）双轨：Mermaid 走「快速看」，需要点击详情时走 X6
统计图表（折线/柱/饼/K线）generate_chartECharts 已有完整体系与配色规范（图表主题同源）
地图 / 平面图 / 电路图不做非「节点 + 边」抽象，X6 无优势
在线编辑画布（拖拽编排）不做L3，见 §6
分流话术（写进工具描述，对齐 generate_chart 风格）

两段式：默认一切图形需求先输出 Mermaid 代码块（轻、快、省 token）； 仅当用户在静态图基础上要求 交互 / 动画 / 数据流动 / 演示播放 / 导出图片， 或明确要求可交互图形时，才调用 render_graph， 把已确认的拓扑转成 GraphIR 重绘（用户无需重新描述）。数据图表 → generate_chart； 地图 / 平面图 / 电路图 → 拒绝。
主动询问：正文输出架构类图后用 options 卡片询问增强方式，把「可交互版（render_graph）」与 「SVG 增强版（draw_svg）」「就这样」一并列为选项；用户选定后再执行，不要自作主张生成。
工具描述里显式写「默认不要调用本工具」，并列出 15 个 kind 及 典型问法（见 §4 每张卡片底部的"典型问法"），升级重绘时一次选对。
