# 弃程票（甩尾）推荐 · 设计（034）

> 日期：2026-11-03 ｜ 类型：design ｜ 状态：**P1 + P2（多程/open-jaw）已实施**
> 依赖：033 低价机票猎人（多目的地枚举与 OTA 抓价）/ 028 A2UI（`flight_board` 确定性 IR）
> 触发：用户提出「机票查询需要智能推荐在真实目的地中转、甩尾的航班，有时候这样更便宜」
> 代码：`divine-server/app/tools/flight/hidden_city.py`（新）、`flight/planner.py`、`adapters/flight_board.py`、`flight/compare.py`

## 1. 口径（先钉死，避免做成别的东西）

**经典弃程（hidden-city / throwaway ticketing）**：票面终点比真实目的地更远，在**中转点**下机。
本质只有一条规则：**弃掉的必须是这张票的最后一程**——后面没有航段，才不会牵连任何东西。

**形态一（去程方向）**

```
目的地：成都
直飞：上海 → 成都            ¥1200
弃程：上海 → 成都 → 拉萨      ¥700   ← 在成都下机，成都→拉萨这段不上飞机
```

**形态二（回程方向，往往更划算，也最容易被漏掉）**

```
去程：上海 → 清迈           正常买
回程直飞：清迈 → 上海        ¥1400
回程弃程：清迈 → 上海 → 南京  ¥900   ← 在上海下机，弃掉上海→南京（这正是最后一程）
```

回程这条的关键：该票的**起点是清迈**，不能用 `conditions.from_city`（上海）去描述，
所以报价行需要行级 `from`（见 §2）。

明确**不是**这些（都在射程之外，见 §6）：

- 不是「从周边城市出发」（异地出发）；
- 不是「更便宜的正常中转航班」——那种是合法可用的报价，属于主列表；
- 不是「跳过第一段」（no-show 首段会让后续航段直接作废）。

## 2. 为什么必须先改数据契约

`flight_board` 的架构是**模型抓价 → 服务端确定性出 IR**（面板不靠模型产 JSON）。原 `rows` 只有
`to / depart / ret / price / airline / direct / dep_time / arr_time / duration / source`，**没有航段**。
而「这趟票经过哪、我打算在哪下机」是**事实**，只有模型在 OTA 页面上真看到才拿得到——服务端无法推算。

因此新增三个字段（都在 `flight_board` 的入参 schema 里）：

| 字段 | 层 | 含义 |
| --- | --- | --- |
| `rows[].via` | 报价行 | 中转/经停城市，按顺序，不含出发地与票面终点。**抓不到航段就不准填** |
| `rows[].skip_at` | 报价行 | 计划下机的城市（= 用户真实目的地，且 ≠ `to`） |
| `rows[].from` | 报价行 | 该行的出发城市，缺省 = `conditions.from_city`。**回程/异地出发必须填**，否则「实际乘坐」会被描述成从出发城市起飞 |
| `rows[].legs` | 报价行 | 多程整程航段 `[{from,to,date}]`：**一行 = 一个完整行程**，`price` 是全程总价（见 §9） |
| `conditions.target_city` | 条件 | 用户真正的目的地（单值），用于**自动识别**没填 `skip_at` 的弃程票 |
| `conditions.trip_type` / `conditions.legs` | 条件 | `one_way` / `round_trip` / `multi_city`；多程给有序航段（缺省时按「有 legs → 多程 / 有 return_date → 往返 / 否则单程」推断） |

三层判定（`hidden_city.split()`），**只做确定性识别，不猜航线**：

1. 显式 `skip_at` 优先；
2. 否则 `via` 里出现 `target_city` 且 ≠ 票面终点 → 提升；
3. 两者都没有 → 就是普通报价，留在主列表。

## 3. 判定与排序

`app/tools/flight/hidden_city.py`（纯函数，无 IO）：

- **提升条件**：`skip_at` 非空 **且** 该行是单程（`ret` 为空）**且** `skip_at != to`；
  **注意口径**：被拒的是「一张往返票」（一个合同下的顺序客票联，弃尾段会让回程一并作废）；
  「往返行程」不等于「往返票」——去程买弃程单程 + 回程另买正常单程是可行组合，
  只要该行本身是单程，**在往返查询里照样会被识别**（有专门用例钉住）；
- **不提升**：往返票（弃尾段会让整张票作废，后段 no-show 回程被取消）、`skip_at == to`（没有尾段可甩）、无 `skip_at` 且 `via` 不含目标城市；
- **省额基准**：**同一出发城市**（行级 `from`，缺省按 `from_city`）、同一出发日、到 `skip_at` 的**最便宜普通单程**。没有基准就显示「—」，**不编数字**；
- **展示字段**：`route` = 该票起点 → 下机城市（用行级 `from`，回程票才不会是「上海 → 上海」）、`tail` = 下机城市 → 票面终点；
- **方向感知配对**（回程弃程引出的必要修复）：回程票的 `to` 是「回程目的地」（上海），不是行程目的地（清迈），
  按原「两行同一 `to`」的配对规则永远配不上对面，**主表会整段消失**。`_pair_one_way` 因此补一条规则：
  去程终点 == 回程起点（`out.to == back.from`）即可配成同一趟往返，仅对带 `from` 的行生效，不影响传统形态。
- **排序**：省得多优先 → 价格升序；
- **上限 3 条**（面板是给人看的，不是报表）。

## 4. 面板结构（`flight_board.build_surface`）

主列表**只放正常票**——便宜的弃程票如果混排会直接顶到第一位，用户容易误点。弃程候选单列一栏：

```
[条件表单]
[摘要]  … ；另有 1 个弃程票更便宜（见下，有限制）
[±N 天推荐表]（不混入弃程票）
────────
也可以这样飞：在成都下机的弃程票（票买到更远的城市，尾段不上飞机）
[弃程表] 实际乘坐 | 弃掉的尾段 | 去程 | 价格 | 比直飞省 | 来源
         上海 → 成都 | 成都 → 拉萨 | 11-20 | ¥700 | 省 ¥500 | 携程
[风险提示 caption / tone=warning] 弃程票限制：必须是单程票（往返票弃尾段会作废整张，含回程）…
```

- 只用既有组件（`Divider` / `Text` / `Table`），**前端零改动**；
- 数据走 `data.hidden`，表格 `rows.path=/hidden`，与主表 `/picks` 同机制；
- 没有候选时**不多出任何节点**（不出现空表、不出现风险提示）；
- 风险文案单一真源：`hidden_city.HIDDEN_RISK_NOTE`，面板与正文转述共用（工具描述要求模型转述时必须保留「弃程的票必须是单程（往返票弃尾段会作废整张，含回程）/ 不能托运行李 / 航司条款可能禁止」）。文案是**纯文本**——面板 `Text` 不解析 Markdown，别写 `**`。

## 5. 顺带修的既有缺陷：单程查询空面板

`planner.recommend()` 原先**一律**把单程报价两两拼成往返（`_pair_one_way`），于是**纯单程查询的候选数是 0**，面板显示「±3 天内没有可用报价」。

这个缺陷恰好卡住本需求：**弃程只能落在单程票上**，主列表必须有可比对象。修法：

```python
if ret_center is None:                       # 单程查询：单程票本身就是结果
    candidates = round_trip + one_way
else:
    candidates = round_trip + _pair_one_way(one_way, window)
```

摘要文案同步：单程时不再说「N 个**往返**候选」（改成「单程候选」），否则用户会以为买到了回程。

## 6. 边界与不做

| 项 | 结论 |
| --- | --- |
| 周边城市出发 | 不做。语义不同（省的是票价、付的是地面交通），可另开需求 |
| 跳过首段 | 不做。no-show 首段会让后续航段作废，本质不可用 |
| 自动枚举「更远的城市」 | 本期不做。需要 033 的多目的地引擎配合（见 §8） |
| 代订 / 代付 | 永远不做（033 已有边界） |
| 航段真实性 | 无法自动校验：没有结构化航段 API，只能靠模型如实填 `via` |

**合规提示必须随结果走**：主流航司运输条款普遍禁止弃程，可能被要求补差价、拒绝承运或影响常旅客权益。产品呈现为「更便宜但有代价」，不做主推。

## 8. 后续（P3 候选）

1. **主动找弃程**：现在是「模型抓到顺带发现」，要变成「智能推荐」还需要枚举更远的目的地（如成都→拉萨/林芝/西宁）× 抓价，可直接复用 033 的目的地枚举与并行搜索。
2. **省额口径升级**：目前基准是「同日同城的普通单程」，若主列表该日无报价就留空；可放宽到 ±N 天窗口并标注日期差。
3. **双向都弃尾**（去程、回程各买一张弃程单程）：单张可行、两张同时弃风险显著更高（同一旅客两次 tail-drop 更容易被承运人识别），暂不做提示与推荐。
4. **`via` 结构化**：若后续接入带航段的 GDS/API，`via` 可改为从 `segments` 推出，届时模型不再手填。
5. **多程的保存/导出**：多程行程目前只有面板表格，若要落附件（033 的 spreadsheet/notes）需要按航段展开。


## 9. P2：多程（open-jaw）支持（同日实施）

**为什么补这一块**：用户指出 OTA 早就有「多程」查询——去 A 回 B（open-jaw）一次查整程，
往往比拆成两个单程便宜。而原面板只有「去程/返程」两列，第三段摆不下；行级 `from` 只是补丁，
多程里 from/to 本来就该是**原生**的段级字段。

**契约**：

```jsonc
"conditions": {
  "from_city": "上海",
  "trip_type": "multi_city",
  "legs": [{"from": "上海", "to": "清迈", "date": "2026-12-01"},
           {"from": "清迈", "to": "南京", "date": "2026-12-08"}]
},
"rows": [
  { "legs": [{"from": "上海", "to": "清迈", "date": "2026-12-01"},
             {"from": "清迈", "to": "南京", "date": "2026-12-08"}],
    "price": 2860, "airline": "MU", "source": "携程" }   // 一行 = 一个完整行程，price = 全程总价
]
```

**实现要点**：

| 位置 | 改动 |
| --- | --- |
| `compare.normalize_offer` | 认 `legs`：`to`/`depart` 由首末航段推出；`ret` 缺省取末段日期（请假/排序需要「结束日」）；`from` 缺省取首段起点 |
| `compare.dedupe` | 去重键加入**航段签名**——同目的地同日期但走法不同是两条不同产品，不能合并 |
| `planner._build_note` | 多程说「多程候选」，且「首选」写**整条路线**（`上海→清迈→南京`），不是末段终点 |
| `flight_board.build_surface` | 多程切列：`航段 / 全程价 / 中转 / 请假 / 连休 / 来源`；行对象**恰好等于列集合**（多一格会被 L2 判不一致） |
| `flight_board.prepare` | `trip_type` 可省略 → 按 legs/return_date 推断；多程允许不填 `depart_date`（取首段日期） |
| `hidden_city` | 多程行程弃尾段**放行**（尾段本来就是最后一程）；`route` 带上前序航段（`上海→清迈 · 清迈→上海`）；多程总价没有可比的单段价 → 省额留空「—」 |

**多程 + 弃程的组合**（真实场景）：`上海→清迈`（去程正常）+ `清迈→上海→南京`（回程多程，在上海下机）
→ 主表给整程总价，弃程栏给「弃掉上海→南京」的那张，两者并排看。

**验证**：新增 5 例（列切换、无 `trip_type` 时自动推断、多程去重保留不同走法、摘要写整条路线、多程末段弃尾）；
`tests/test_flight_board.py` **55 passed**；前端零改动（仍是 `Table`，只换列定义）。

**没做**：多程逐段比价（如「第 2 段单独买更便宜」）——那需要按段报价而不只是整程总价，留待接结构化航段数据后再说。


## 10. P3：主动找弃程（同日实施）

**为什么需要**：P1 只是「模型碰巧抓到带航段的票才识别」。要做到「智能推荐」，必须**主动去查**
比目的地更远的终点——否则用户永远等不到那条便宜票。

**分工（沿用 033 的边界）**：OTA 反爬只认带浏览器的 `web_task`，抓价只能由模型做；
而「该查哪几条」是纯几何问题，放服务端算，省得模型凭感觉编城市。

### 筛选规则（`app/tools/flight/onward.py`，纯函数）

1. 候选城市离**出发地**必须比目的地更远（`> 1.02×`）——否则不可能经目的地中转；
2. 候选城市离**目的地**至少 250km——太近多半是同一机场群，凑不出尾段；
3. 与「出发地→目的地」的**方位角偏差 ≤ 60°**——明显反方向的城市直接排除。

排序：方位偏差小的优先（更像同一走向），其次延伸段近的优先（尾段便宜更容易拼出低价）。
表里有 58 个城市（主干 + 西部/边疆/海岛这类常被"再飞一段"的目的地），支持三字码与
「成都天府」这类别名；未知城市返回空清单，不抛异常。

### 工具（`flight_hidden_targets`）

```jsonc
// 入参
{"from_city": "上海", "target_city": "成都", "limit": 3}
// 出参（data）
{"from_city": "上海", "target_city": "成都",
 "candidates": [{"city": "林芝", "leg_km": 947.9, "bearing_delta": 0.3,
                 "distance_from_origin_km": 2610.4,
                 "reason": "成都再飞约 947km，与主航段同向（偏差 0.3°）"}],
 "how_to": "对下面每条航线各查一次 OTA；命中条件是「中转城市 = 成都」…"}
```

- 只出清单、**不抓价**（抓价仍是 `web_task` + `flight-trip/flight-ctrip` 配方）；
- 挂 `flights` 意图（`_CONTENT_TOOLS`），与 `flight_board` 同源；
- 提示词节新增「主动找弃程」：先拿清单 → 每条实查 → 命中才回填 `to/via/skip_at`，
  **没命中不要硬填**；每条多一次抓价，别超过 3 条、票价本来便宜时不做。

### 已知局限（写清，避免被当成"全自动"）

1. **坐标表 ≠ 航线网络**：真实是否经停由航司决定；本工具只回答"值得一试"，命中率靠实查验证。
2. **国际航段未覆盖**：转机枢纽多在境外（如 香港/曼谷/新加坡），坐标表只有国内城市；
   国际弃程另需签证/入境规则，本期不做。
3. 每多一条候选就多一次浏览器抓价，所以有 `limit ≤ 5` 的硬上限，提示词里再收到 3。

### 验证

新增 `tests/test_flight_onward.py` **12 例**：西向命中（拉萨/稻城/林芝）、反方向排除（哈尔滨/沈阳）、
更近城市排除（重庆）、排序与 limit、IATA/别名解析、未知城市、清单文案（含命中条件与"不要硬填"）、
无候选时的「不适合找弃程」、必填校验、limit 钳制、**注册 + flights 意图挂载**（缺一即等于没做）。
